MODULE 1: Database Architecture
 
Topic 1.1: Client - Server Database Models
 
1. Topic Name — Client - Server Database Architecture
 
What is it?
 Client - server architecture is a way of organizing a database system where 
two kinds of computers work together: a 
client (which asks for data) and a 
server 
(which stores and manages the 
data and answers the request).
 
Why do we need it?
 Before client
- server systems, all processing happened on one 
giant central computer (mainframe), and users only had “dumb terminals” (screens 
with no processing power). This was expensive and hard to scale. Client
- server 
architecture splits the work, so: 
- Many users can work at the same time. 
- The heavy 
work of storing and protecting data stays in one safe place (the server). 
- The client can 
have a friendly, fast user interface.
 
Where is it used?
 - Bankin g systems (ATM = client, bank database = server) 
- College 
portals (your browser = client, college server = server) 
- Online shopping websites 
- 
Almost every modern application that uses a database
 
Important: Client - server is not one fixed design 
— it comes in different “tiers” (2
- tier, 
3- tier), which we will study in detail.
 
2. Beginner Friendly Introduction
 
Imagine you go to a restaurant. You (the 
client ) do not cook your own food. You tell 
the waiter what you want. The waiter passes your order to the kit
chen (the 
server ), 
and the kitchen prepares the food and sends it back through the waiter.
 
In computers: 
- Client = the program you use directly (browser, mobile app, desktop 
app). - Server = the powerful computer that stores the actual database and does the 
heavy processing. 
- Request = what the client asks for (e.g., “show me all students”). 
- 
Response = what the server sends back (e.g., the list of students).
 
Technical words explained simply:

3. Real - Life Analogies
 
Analogy 1 — Restaurant: You (client) order food. The waiter carries your order to the 
kitchen (server). The kitchen prepares it and the waiter (net
work) brings it back. You 
never enter the kitchen yourself 
— this keeps the kitchen organized and safe, just like a 
database server stays protected from direct user access.
 
Analogy 2 — Bank Branch and Head Office:
 A local bank branch (client) does not keep 
all account records; it always checks with the head office computer (server) before 
giving you money. This way, all data stays consistent across every branch, just like a 
database server keeps data consistent for every client.
 
4. Complete Detailed Explana
tion 
4.1 Two - Tier Client
- Server Architecture
 
In a two - tier architecture, there are exactly two layers: 
 
1. Client Tier
 – contains the user interface AND the application/business logic. 
 
2. Server Tier
 – contains the database (data storage and query processing).
 
The client talks 
directly to the database server, usually using a standard protocol such 
as ODBC (Open Database Connectivity) or 
JDBC (Java Database Connectivity).
 
Components: 
 - Client application (contains UI + business rules) 
 
- Network connection
  
- Database server (stores data, executes SQL, returns results)
 
Working: The client builds an SQL query, sends it directly to the database server over 
the network, the server executes it and sends back the result set, and the client 
displays it. 
Advantages: - Simple to build and understand 
- Fast for small numbers of users (fewer 
hops) - Good for LAN
- based systems within one organization

Limitations:
 - Every client machine needs the correct drivers/business logic installed 
(hard to update) 
- Does not scale
 well — too many direct connections overload the 
server - Business logic mixed with UI code makes maintenance difficult 
- Security risk 
— clients directly touch the database
 
4.2 Three - Tier Client
- Server Architecture
 
In a three - tier architecture, the work is split into three separate layers: 
 
1. Presentation Tier (Client)
 – only handles the user interface (what the user sees and 
clicks).  
2. Application Tier (Business Logic / Middle Tier)
 – contains all business rules, 
validation, and processing. This tier t
alks to the database on behalf of the client. 
 
3. Data Tier (Database Server)
 – stores and manages the actual data.
 
Working (Step by step):
  
1. Client sends a request (e.g., clicks “Submit Order”) to the Application Server. 
 
2. Application Server applies business rules (e.g., “check if stock is available”). 
 
3. Application Server builds and sends the SQL query to the Database Server. 
 
4. Database Server executes the query and returns data to the Application Server. 
 
5. Application Server processes/formats t
he result and sends it back to the Client.
 
Advantages: - Clients are “thin” 
— they don’t need heavy installation, just a browser 
- 
Business logic is centralized 
— easy to update once, applies to everyone 
- Better 
security 
— clients never touch the database directly 
- Scales well 
— multiple 
application servers can be added (load balancing) 
- Supports many concurrent users, 
ideal for internet/web applications
 
Limitations:
 - More complex to design, build, and debug 
- More network 
communication (extra hop) can 
add slight delay 
- Requires more hardware/servers, so 
higher initial cost
 
Exam Tip: A very common exam question is “Differentiate between two
- tier and three
-
tier architecture.” Always mention: number of layers, where business logic sits, 
scalability, and typical use case.

4.1 Why Concurrency Problems Happen

A lock is a mechanism that stops other t

4.4 Two - Phase Locking (2PL) Protocol
 
Two - Phase Locking is the most famous lock
- based protocol that guarantees 
serializability
 (the result is as if transactions ran one after another).
 
It has exactly two phases: 
 
1. Growing Phase
 — the transaction can 
acquire (get) locks, but cannot release any 
lock.  
2. Shrinking Phase
 — the transactio
n can release locks, but cannot acquire any new 
lock. 
Once a transaction releases even a single lock, it enters the shrinking phase and can 
never request a new lock again.
 
 
Variations of 2PL:
  
- Basic 2PL
 — as described above; can still suffer from cascading rollbacks (if a 
transaction fails, others that read its uncommitted data must also roll back). 
 
- Strict 2PL
 — all exclusive locks are held until the transaction 
commits or aborts . This 
avoids cascading rollbacks and dirty reads. Most commercial databas
es use Strict 2PL. 
 
- Rigorous 2PL
 — both shared and exclusive locks are held until commit/abort. Even 
simpler to reason about, slightly more restrictive than strict 2PL. 
 
- Conservative (Static) 2PL
 — a transaction must acquire 
all the locks it will ever need 
before it starts executing. This avoids deadlock completely but is hard to use in 
practice since you must know all data items in advance.

- Wait.  
- Deadlock Detection
 — using a “wait
- for graph” to detect cycles and then aborting

Topic 4.1: Basics of Transactions and ACID Properties
 
1. Topic Name — Transactions and ACID Properties
 
What is it?
 A transaction
 is a single logical unit of work in a database, made up of one 
or more operations, that must be executed completely or not at all. 
ACID is a set of 
four properties (Atomicity, Consistency, Isolation, Durability) that guarantee 
transactions are processed reliably.
 
Why do we need it?
 Without these guarantees, a system crash or concurrent access 
could leave data in a broken, inconsistent, or partially updated state 
— a serious risk for 
critical systems like banking.
 
Where is it used?
 - Banking and financial systems 
- E- commerce order processing 
- 
Airline reservation systems 
- Any system where correctness of multi
- step operations 
matters 
2. Beginner Friendly Introduction
 
Think of transferring money from Account A to Account B. This requires two steps: 
subtract from A, 
add to B. If the system crashes after subtracting but before adding, 
money disappears! A transaction bundles both steps together so that either 
both 
happen, or neither happens. 
Key words explained:
 
Word 
Simple Meaning
 
Transaction
 
A group of operations treated as one single unit
 
Commit 
Successfully finishing and saving a transaction permanently
 
Rollback 
Undoing a transaction’s changes because something went wrong
 
Atomicity 
All- or- nothing execution
 
Durability 
Once saved, data survives even a crash
 
3. Re al- Life Analogies
 
Analogy 1 — Money Transfer:
 Withdrawing cash from one envelope and putting it in 
another envelope must happen together 
— you would never want to take money out 
and then simply lose it if you got interrupted halfway.

4. Complete Detailed Explanation
 
4.1 What is a Transaction?
 
A transaction moves a database from one 
consistent state
 to another. It typically ends 
with either: 
- Commit — all changes are made permanent. 
- Rollback (Abort)
 — all 
changes are undone, as if the transaction never happened.
 
4.2 The ACID Properties
 
1. 
Atomicity — a transaction is treated as a single, indivisible unit; either 
all its 
operations complete successfully, or 
none of them do. If any step fails, the entire 
transaction is rolled back.
 
2. 
Consistency
 — a transaction must take the databas
e from one valid state to 
another valid state, preserving all defined rules (constraints, triggers) 
— it should 
never leave the database violating its own rules.
 
3. 
Isolation — concurrently executing transactions should not interfere with each 
other; the result should be as if transactions ran one after another (serially), even 
though they may actually run concurrently for performance.
 
4. 
Durability — once a transaction commits, its changes are permanent and will 
survive even a system crash or power failure (usua
lly achieved by writing 
changes to non
- volatile storage/logs).
 
4.3 Transaction States
 
A transaction moves through these states during its lifecycle: 
- Active — the 
transaction is currently executing. 
- Partially Committed
 — the final operation has 
executed, but changes aren’t yet permanently saved. 
- Committed — the transaction 
has completed successfully, and changes are permanent. 
- Failed — an error occurred, 
and the transaction cannot proceed. 
- Aborted — the transaction has been rolled back, 
and the dat abase restored to its state before the transaction began.

↓

↓ Yes → Partially Committed 
→ Commit (Durable, Permanent)
 
↓ No → Failed → Rol lback → Aborted (Database restored to original state)

1. Topic Name — Long Duration Transactions and Implementation Issues
 
What is it? A long - duration transaction
 is a transaction that 
runs for a very long time 
(minutes, hours, or even days) 
— much longer than the typical short banking 
transaction 
— often because it involves human decision
- making or many connected 
steps. Because standard transaction techniques (like holding locks for the whole 
duration) don’t work well for such long transactions, special 
implementation 
techniques — nesting, compensation, and specialized concurrency control 
— are used. 
Why do we need it?
 If a long transaction held locks on data for hours or days (like 
stan dard 2PL would require), it would block other users for an unacceptably long time. 
Special techniques are needed to keep the system usable while still preserving 
correctness as much as possible.
 
Where is it used?
 - Collaborative document editing over long periods 
- Complex 
engineering design processes (CAD projects) 
- Long - running business processes (loan 
processing, insurance claims) 
- Travel booking systems (reserving flights, hotels, and 
cars together)

Imagine booking a

hotel booking fails after the flight is already booked, you don’t want to hold the flight 
seat locked for hours while you sort things out 
— you’d rather book the flight, and if 
something later fails, simply 
cancel (compensate) that booking instead. This is the core 
idea behind handling long
- duration transactions.

4. Complete Detailed Explanation
 
4.1 Why Standard Tra
nsactions Don’t Work Well for Long Durations
 
• 
Standard concurrency control (like Strict 2PL) holds locks until commit 
— fine 
for transactions lasting milliseconds/seconds, but very damaging if held for 
hours/days (other users get blocked for far too long).
 
• 
Rolling back a long transaction entirely (as in a normal ACID rollback) can be 
extremely wasteful if most of the work was actually valid and just one small part 
failed. 
4.2 Nested Transactions
 
• 
A nested transaction
 breaks a large transaction into a hierarch
y of smaller 
sub -
transactions
. 
• 
Each sub - transaction can commit or abort somewhat independently.
 
• 
If a sub - transaction fails, only that portion (and its own nested sub
- transactions) 
needs to be rolled back 
— not the entire outer transaction.
 
• 
The overall (top
- level) transaction still ultimately commits or aborts as a whole, 
but nesting provides more fine
- grained control and partial recovery.
 
4.3 Compensating Transactions
 
• 
Since a long transaction may have already 
committed some of its sub
- parts 
before a later f
ailure occurs, a normal rollback isn’t possible (the data is already 
permanently saved and possibly used by others).
 
• 
A compensating transaction
 is a separate transaction specifically designed to 
logically “undo” or reverse the effect of an earlier committed transaction (e.g., a 
“cancel booking” transaction reversing a “make booking” transaction).

4.4 Concurrency Control for Long

Since traditional locking is too restrictive for long transactions, alternative 
concurrency approaches are used: 
- Optimistic Concurrency Control
 — allow the

- Relaxed Isolation Levels

running processes, when perfect isolation isn’t strictly necessary.

Topic 5 .2: Introduction to Business Intelligence
 
1. Topic Name — Business Intelligence (BI)
 
What is it?
 Business Intelligence (BI)
 refers to the technologies, tools, and processes 
used to collect, integrate, analyze, and present business data to support better 
decision - making by managers and executives.
 
Why do we need it?
 Raw data and even data mining results need to be presented in a 
clear, usable way (dashboards, reports) so that business leaders can quickly understand 
trends and make informed decisions.
 
Where i s it used? - Executive dashboards 
- Sales and marketing performance tracking 
- Financial forecasting 
- Operational efficiency monitoring

4. Complete Detailed Explanation
 
4.1 Multimedia Databases
 
• 
Store and manage 
multimedia data types
: images, audio, video, and 
combinations of these (unlike traditional databases limited to text/numbers).
 
• 
Require special indexing and retrieval techniques, since searching “find images 
similar to this one” is very different from searching “find rows where age > 20.”
 
• 
Content - Based Retrieval
 allows searching based on actual visual/audio features 
(color, shape, texture, pitch), rather than relying only on manually added text 
tags/descriptions.
 
• 
Challenges include very large file sizes, the need for 
efficient compression, and 
complex similarity
- based searching (rather than exact matching).
 
4.2 Mobile Databases
 
• 
Designed to run on, or be accessed by, mobile/portable devices (smartphones, 
tablets, laptops in the field).
 
• 
Must handle intermittent connectivity
 — devices may lose network connection 
and need to continue working offline.
 
• 
Use synchronization
 mechanisms to update the central database once the 
device reconnects, resolving any conflicts that occurred during offline use.
 
• 
Often need to be lightweight
 
(efficient on limited device 
storage/battery/processing power).
 
4.3 Digital Databases
 
• 
Broadly refers to databases that manage large collections of 
purely digital 
content/assets
 — such as digital libraries, e
- books, scanned archives, and digital 
media repositories.
 
• 
Focuses on organizing, cataloging, preserving, and enabling efficient 
search/retrieval of digital assets over the long term.
 
• 
Often incorporates metadata (descriptive information about each digital item) to 
support searching and browsing large col
lections.
